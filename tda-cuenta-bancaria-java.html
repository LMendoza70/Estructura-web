Tipos de Datos Abstractos (TDA): la caja cerrada

Un TDA separa qué puede hacer un dato de cómo lo hace por dentro. Quien lo usa solo ve las operaciones; nunca toca la implementación directamente.

Este es el TDA CuentaBancaria: por fuera, un conjunto de operaciones. Por dentro, datos protegidos que solo el propio TDA puede modificar.

01 · Idea central (técnica Feynman)

¿Qué es un Tipo de Dato Abstracto?

Un TDA es un modelo matemático de un dato, definido únicamente por qué operaciones se le pueden hacer y qué garantías cumplen esas operaciones — sin decir nada de cómo están programadas por dentro.

Analogía: piensa en un cajero automático. Tú insertas tu tarjeta, retiras dinero, consultas tu saldo. Nunca ves los circuitos, los billetes reales moviéndose en los cajones internos, ni la base de datos del banco. El cajero te da una interfaz de operaciones y esconde por completo el mecanismo. Eso es exactamente lo que hace un TDA con una clase en Java.

En Java, un TDA se implementa como una clase donde los atributos son private y el único punto de contacto con el mundo exterior son los métodos públicos. No necesitas una interface para lograr esto: la abstracción ya la da el encapsulamiento con modificadores de acceso.

Formalmente, un ADT se compone de:

  • Dominio de valores: el conjunto de elementos válidos (por ejemplo, saldos no negativos).
  • Operaciones disponibles: qué acciones se permiten, qué parámetros reciben y qué devuelven (depositar, retirar, consultarSaldo).
  • Reglas o axiomas: propiedades que garantizan coherencia (retirar nunca deja el saldo en negativo; depositar con monto positivo aumenta el saldo).

La clave es que un ADT no explica cómo lograrlo; sólo define qué debe suceder. Así separamos preocupaciones: un equipo puede concentrarse en la interfaz y otro en la implementación.

02 · Anatomía de un TDA

Especificación vs. implementación

Especificación (el contrato)

Las operaciones disponibles y lo que prometen: "depositar aumenta el saldo", "retirar nunca deja el saldo en negativo". Es lo único que le importa a quien usa la clase.

Implementación (el secreto)

Cómo se guarda el saldo, qué validaciones internas se hacen, en qué orden se ejecutan las instrucciones. Puede cambiar sin que el código que usa la clase se entere.

Al elegir una implementación, considere:

  • Complejidad temporal: algunas operaciones deben ser O(1) o O(log n).
  • Restricciones de concurrencia: operaciones atómicas o versiones inmutables para entornos multihilo.
  • Garantías adicionales: orden estable, ausencia de duplicados, prioridades.
public class CuentaBancaria {

    // ---- implementación oculta ----
    private double saldo;
    private String titular;
    private String numeroCuenta;

    // ---- constructor: única forma de crear el dato ----
    public CuentaBancaria(String titular, String numeroCuenta) {
        this.titular = titular;
        this.numeroCuenta = numeroCuenta;
        this.saldo = 0.0;
    }

    // ---- especificación: operaciones públicas del TDA ----
    public void depositar(double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("El monto debe ser positivo");
        }
        saldo += monto;
    }

    public void retirar(double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("El monto debe ser positivo");
        }
        if (monto > saldo) {
            throw new IllegalStateException("Fondos insuficientes");
        }
        saldo -= monto;
    }

    public double consultarSaldo() {
        return saldo;
    }

    public String obtenerTitular() {
        return titular;
    }
}

Nótese que no hay ninguna interfaz aquí. La abstracción se logra solo con la palabra private en los atributos y exponiendo únicamente los métodos que forman el contrato del TDA. El compilador impide que código externo escriba cuenta.saldo = -500; directamente, porque saldo no es visible fuera de la clase.

04 · Errores frecuentes

Lo que rompe un TDA

⚠
Atributos públicos o con get/set sin validación: si expones public double saldo; o un setSaldo(double s) que acepta cualquier valor, cualquiera puede romper el invariante "el saldo nunca es negativo".
⚠
Devolver referencias internas mutables: si un método público retorna directamente un arreglo o lista interna, quien la reciba puede modificarla desde afuera sin pasar por las operaciones del TDA.
⚠
Confundir TDA con interfaz de Java: el TDA es el concepto (qué operaciones + qué garantías); la interface es solo una herramienta del lenguaje para declararlo formalmente. Se puede construir un TDA perfectamente válido usando solo una clase con encapsulamiento, como en este ejemplo.
⚠
Ignorar los axiomas del ADT: si una operación rompe una regla garantizada (ej. "retirar permite saldo negativo"), el código que usa el TDA puede comportarse de manera impredecible. Siempre validar antes de modificar el estado interno.
05 · Principio de Pareto

El 20% de reglas que explica el 80% de los TDA

  • Todo atributo que representa el estado interno debe ser private.
  • Las únicas puertas de entrada y salida son los métodos públicos: ellos definen el contrato.
  • Cada operación pública debe mantener el dato en un estado válido (el invariante), rechazando lo que lo rompa.
  • Quien usa el TDA no necesita saber cómo está implementado por dentro, solo qué promete cada operación.
  • Si el estado interno cambia de representación (por ejemplo, de double a un objeto Dinero), el código que usa la clase no debería tener que cambiar.
  • Un ADT permite múltiples implementaciones según las necesidades de rendimiento, memoria o complejidad; el contrato se mantiene igual.
07 · Múltiples implementaciones

Ponte a prueba (haz clic en cada pregunta)

1. ¿Qué hace que CuentaBancaria sea un TDA y no solo una clase cualquiera?
Que separa claramente qué operaciones ofrece (depositar, retirar, consultar saldo) de cómo las implementa, y protege su estado interno con encapsulamiento, de forma que solo se puede modificar a través de esas operaciones.
2. ¿Se necesita una interface de Java para construir un TDA?
No. El TDA es un concepto de diseño; se puede lograr solo con una clase que use modificadores de acceso (private) para ocultar su estado y exponga únicamente métodos públicos como contrato.
3. ¿Por qué es un error exponer public double saldo; directamente?
Porque cualquier código externo podría asignarle un valor negativo o inconsistente sin pasar por las validaciones de depositar() o retirar(), rompiendo el invariante del TDA.
4. Si mañana cambias cómo se almacena el saldo internamente, ¿debería afectar al código que usa CuentaBancaria?
No debería, siempre que la especificación (los métodos públicos y lo que garantizan) se mantenga igual. Ese es precisamente el valor de separar especificación de implementación.
