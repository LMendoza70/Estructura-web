Java vs C#: diferencias de sintaxis

Catorce diferencias clave para trabajar aplicaciones de consola orientadas a objetos, con el código exacto lado a lado — pensada para quien ya conoce uno de los dos lenguajes y necesita ubicarse rápido en el otro.

01

Punto de entrada del programa

Ambos lenguajes exigen un método Main como punto de arranque, pero difieren en la capitalización del nombre del método y en si es obligatorio envolverlo en una clase.

Java
public class Programa {
    // "main" en minúscula: exacto, Java distingue mayúsculas/minúsculas
    public static void main(String[] args) {
        System.out.println("Inicio");
    }
}
C#
class Programa
{
    // "Main" con M mayúscula
    static void Main(string[] args)
    {
        Console.WriteLine("Inicio");
    }
}
// C# moderno también permite "top-level statements":
// un archivo .cs sin clase ni Main explícito, solo el código directo.
02

Imprimir en consola

La clase y el método cambian de nombre, pero el comportamiento (con o sin salto de línea) es equivalente.

Java
System.out.println("Con salto de línea");
System.out.print("Sin salto de línea");
System.out.printf("Nombre: %s, edad: %d%n", nombre, edad);
C#
Console.WriteLine("Con salto de línea");
Console.Write("Sin salto de línea");
Console.WriteLine($"Nombre: {nombre}, edad: {edad}");
03

Leer entrada del usuario

Java necesita instanciar un objeto Scanner explícitamente; C# lee directo desde la clase estática Console.

Java
import java.util.Scanner;

Scanner entrada = new Scanner(System.in);
System.out.print("Nombre: ");
String nombre = entrada.nextLine();
System.out.print("Edad: ");
int edad = entrada.nextInt();   // hay que convertir según el tipo
C#
Console.Write("Nombre: ");
string nombre = Console.ReadLine();
Console.Write("Edad: ");
int edad = int.Parse(Console.ReadLine());  // ReadLine siempre da string
En C#, Console.ReadLine() siempre devuelve string; conviertes tú mismo con int.Parse o int.TryParse. En Java, Scanner ofrece un método específico por tipo (nextInt(), nextDouble()...).
04

Paquetes vs espacios de nombres

Java organiza el código en paquetes que reflejan la estructura de carpetas; C# usa namespaces, que son lógicos y no dependen de dónde esté físicamente el archivo.

Java
// Debe coincidir con la ruta de carpetas: com/uthh/edd/unidad1
package com.uthh.edd.unidad1;

import java.util.List;
import java.util.ArrayList;
C#
// No depende de la carpeta física del archivo
namespace Uthh.Edd.Unidad1;

using System.Collections.Generic;
05

Declaración de clases y modificadores de acceso

La sintaxis de la clase es casi idéntica; la diferencia importante está en el modificador de acceso por defecto cuando no escribes ninguno.

Java
public class Empleado {
    private String nombre;   // solo esta clase
    double salario;             // sin modificador = "package-private":
                                 // visible solo dentro del mismo paquete
    protected int antiguedad; // clase + subclases (incluso en otro paquete)
    public String puesto;
}
C#
public class Empleado
{
    private string nombre;      // solo esta clase
    double salario;                // sin modificador = "private" por defecto
                                    // (distinto a Java: aquí NO es visible
                                    // ni siquiera para otras clases del mismo namespace)
    protected int antiguedad;
    internal string puesto;    // visible en todo el mismo ensamblado (.dll/.exe);
                                    // no tiene equivalente directo en Java
}
Cuidado con el default: un miembro sin modificador en Java es visible para todo el paquete; en C# es private, el más restrictivo. Es la trampa más común al cambiar de lenguaje.
06

Propiedades automáticas vs getters/setters

C# tiene sintaxis nativa de "propiedades"; Java no — el patrón getter/setter se escribe siempre a mano (o se genera con el IDE).

Java
public class Producto {
    private double precio;

    public double getPrecio() {
        return precio;
    }
    public void setPrecio(double precio) {
        if (precio < 0) throw new IllegalArgumentException();
        this.precio = precio;
    }
}
C#
public class Producto
{
    // Propiedad automática simple
    public string Nombre { get; set; }

    // Propiedad con lógica personalizada (equivalente al getter/setter de Java)
    private double _precio;
    public double Precio
    {
        get => _precio;
        set
        {
            if (value < 0) throw new ArgumentException();
            _precio = value;
        }
    }
}
07

Constructores y llamada al constructor de la clase padre

Misma idea, distinta palabra clave para invocar al constructor de la superclase: super() en Java, base() en C#.

Java
public class Persona {
    protected String nombre;
    public Persona(String nombre) { this.nombre = nombre; }
}

public class Empleado extends Persona {
    private double salario;
    public Empleado(String nombre, double salario) {
        super(nombre);         // llama al constructor de Persona
        this.salario = salario;
    }
}
C#
public class Persona
{
    protected string Nombre;
    public Persona(string nombre) { Nombre = nombre; }
}

public class Empleado : Persona
{
    private double salario;
    public Empleado(string nombre, double salario)
        : base(nombre)          // llama al constructor de Persona
    {
        salario = salario;
    }
}
08

Herencia y sobrescritura de métodos

Java permite sobrescribir cualquier método no final por defecto. C# exige que el método padre se declare explícitamente virtual para poder sobrescribirlo con override.

Java
public class Figura {
    public double calcularArea() { return 0; }
}

public class Circulo extends Figura {
    private double radio;

    @Override   // anotación: opcional pero muy recomendada
    public double calcularArea() {
        return Math.PI * radio * radio;
    }
}
C#
public class Figura
{
    // SIN "virtual" aquí, Circulo NO podría sobrescribir este método
    public virtual double CalcularArea() { return 0; }
}

public class Circulo : Figura
{
    private double radio;

    public override double CalcularArea()   // "override" es obligatorio, no opcional
    {
        return Math.PI * radio * radio;
    }
}
La diferencia real: en Java, "se puede sobrescribir" es el comportamiento por defecto (a menos que marques final). En C#, "no se puede sobrescribir" es el default, y tienes que habilitarlo explícitamente con virtual + override.
09

Interfaces

Java usa una palabra clave distinta para heredar de una clase (extends) e implementar una interfaz (implements). C# unifica ambas bajo el mismo símbolo :.

Java
public interface Imprimible {
    void imprimir();
}

public class Factura implements Imprimible {
    @Override
    public void imprimir() {
        System.out.println("Factura impresa");
    }
}
C#
public interface IImprimible
{
    void Imprimir();
}

public class Factura : IImprimible   // mismo ":" que se usa para heredar de una clase
{
    public void Imprimir()
    {
        Console.WriteLine("Factura impresa");
    }
}
Convención de nombres: en C# las interfaces casi siempre empiezan con I (IImprimible). En Java no existe esa convención; el nombre va sin prefijo (Imprimible).
10

Colecciones genéricas

La sintaxis de genéricos es prácticamente idéntica; cambian los nombres de las clases y de qué paquete/namespace se importan.

Java
import java.util.List;
import java.util.ArrayList;
import java.util.Map;
import java.util.HashMap;

List<String> nombres = new ArrayList<>();
nombres.add("Ana");

Map<String, Integer> edades = new HashMap<>();
edades.put("Ana", 30);
C#
using System.Collections.Generic;

List<string> nombres = new List<string>();
nombres.Add("Ana");

Dictionary<string, int> edades = new Dictionary<string, int>();
edades.Add("Ana", 30);
El "diccionario" de Java es HashMap; en C# es Dictionary. La lógica y las operaciones (agregar, buscar por clave, recorrer) son conceptualmente las mismas.
11

Formato e interpolación de cadenas

C# tiene interpolación nativa con $"..." desde hace años; Java la incorporó como preview reciente (string templates), así que en cursos y proyectos actuales lo más común sigue siendo String.format o concatenación.

Java
String nombre = "Ana";
int edad = 30;

// Forma más común y estable en Java:
String mensaje = String.format("%s tiene %d años", nombre, edad);

// También válido: concatenación simple
String otro = nombre + " tiene " + edad + " años";
C#
string nombre = "Ana";
int edad = 30;

// Interpolación nativa, forma estándar en C# moderno:
string mensaje = $"{nombre} tiene {edad} años";
12

Manejo de excepciones

La sintaxis try/catch/finally es la misma. La diferencia importante: Java distingue entre excepciones chequeadas (obligan a declarar throws en la firma del método) y no chequeadas; C# no tiene ese concepto.

Java
// IOException es "chequeada": el método debe declararla
public void leerArchivo() throws IOException {
    try {
        // código que puede fallar
    } catch (IOException e) {
        System.out.println("Error: " + e.getMessage());
    } finally {
        System.out.println("Siempre se ejecuta");
    }
}
C#
// No existe el concepto de excepción "chequeada": nunca se declara en la firma
public void LeerArchivo()
{
    try
    {
        // código que puede fallar
    }
    catch (IOException e)
    {
        Console.WriteLine($"Error: {e.Message}");
    }
    finally
    {
        Console.WriteLine("Siempre se ejecuta");
    }
}
13

Constantes

Java usa final (combinado con static para constantes de clase). C# tiene dos palabras distintas según si el valor se conoce en tiempo de compilación o de ejecución.

Java
public static final double IVA = 0.16;
public final String id;   // se asigna una sola vez, en el constructor
C#
public const double IVA = 0.16;         // valor fijo en tiempo de compilación
public readonly string Id;         // se asigna una sola vez, en el constructor
                                    // (equivalente real a "final" de Java)
final de Java se parece más a readonly de C# que a const — const en C# exige un valor calculable en tiempo de compilación, mientras que readonly/final pueden asignarse dentro del constructor.
14

Comparar igualdad de objetos

El operador == se comporta distinto entre ambos lenguajes al comparar objetos — una fuente frecuente de errores al cambiar de uno a otro.

Java
String a = new String("hola");
String b = new String("hola");

a == b;          // false: compara referencias (misma dirección en memoria)
a.equals(b);      // true: compara contenido — así se comparan objetos en Java
C#
string a = new string("hola".ToCharArray());
string b = new string("hola".ToCharArray());

a == b;           // true: C# sobrecarga "==" para string y compara CONTENIDO
a.Equals(b);      // también true, mismo resultado
// Para tus propias clases, "==" SÍ compara referencia salvo que
// sobrecargues el operador explícitamente (Java no permite sobrecargar operadores).
Regla práctica: en Java, usa siempre .equals() para comparar contenido de objetos (incluido String) y nunca == salvo que quieras comparar referencias a propósito.
